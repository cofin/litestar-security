# Providers False-Positive Suppressions

Do not flag the following intentional patterns in `src/litestar_security/providers/`:

- **FP-PRV-01 (Unverified JWT header/payload pre-inspection in `CompositeBearerConfig`)**: `_bearer.py` uses `parse_unverified_jwt_route` to inspect the unverified JWS header (`typ`) and payload (`iss`, `aud`) strictly to select which `BearerTokenSlot` owns the token (`BearerSlotSelector` matches `issuers`, `token_types`, `audiences`, never `kid`); the matched `BearerTokenSlot.verifier` (`JWTVerifier`) always performs full cryptographic signature and claim verification before accepting the token.
- **FP-PRV-02 (Direct IP URL rewrite in `OAuthProviderClient._pinned_endpoint`)**: Rewriting the outbound `httpx.Request` URL host to the resolved literal IP address while setting `Host` and `extensions["sni_hostname"]` is the deliberate DNS-rebinding / SSRF defense (distinct from `HttpxJWKSFetcher` and `OIDCDiscoveryClient`, which validate resolved DNS IPs and stream the original HTTPS URL).
- **FP-PRV-03 (`asyncio.shield` around shared JWKS refresh task)**: `CachedJWKSProvider._refresh_singleflight` shields `coordination.refresh.task` so cancellation of one caller does not abort the refresh for concurrent waiters.
- **FP-PRV-04 (Raw API key returned once on `IssuedAPIKey`)**: `APIKeyService.issue` and `rotate` return `IssuedAPIKey(key_id=..., value=...)` once at creation/rotation time; only the domain-separated HMAC-SHA256 `APIKeyState.digest` is persisted in `APIKeyStore`.
- **FP-PRV-05 (`BufferedAPIKeyUsage` deferred flush & capacity drop)**: Usage tracking via `APIKeyUsageSink.record(key_id=..., used_at=...)` is non-authoritative telemetry: `observe()` coalesces per `key_id`, drops new entries when `len(_pending) >= self.capacity` without inline I/O, and flushes on `flush()` or shutdown (`BufferedAPIKeyUsage.close()` / `APIKeyService.close()`).
- **FP-PRV-06 (`APIKeyConfig(accept_authorization_bearer=True)` outside `CompositeBearerConfig`)**: `_APIKeyCredentialSlot` intentionally stays on its dedicated `"api-key"` slot rather than `CompositeBearerConfig`; `AuthenticationRegistry._coordinate_bearer_slots` updates `_BearerCredentialSlot.excluded_prefixes` (or wraps custom Bearer slots in `_PrefixExcludingBearerSlot`), and `_plan_uses_bearer` inspects `additional_security_schemes` (`APIKeyBearer`) for RFC 9728 discovery challenges.
